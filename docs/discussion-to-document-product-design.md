# 玄鸟：从讨论到文档成果的产品设计

> 状态：本地实现与验收依据。P0-A 至 P2 的交付情况、使用说明和验证范围见[实施记录](discussion-workspace-implementation.md)。
>
> 日期：2026-09-05
>
> 范围：上下文引用、分支收敛、成果回写、回答操作与结果追踪、工作视图、项目总览六项能力。

## 1. 产品目标与现状

玄鸟围绕本地 Markdown 文档组织可分支、可追溯的 AI 讨论。本设计将这一流程延伸为：

**明确讨论依据 → 展开方案 → 比较与收敛 → 采纳到文档或据此执行 → 追踪实际结果。**

用户应当能够回答四个问题：本次讨论参考了什么，为什么形成这个结论，结论改动了哪里，还有哪些事情没有完成。

设计起点已有文本锚定、讨论树、节点类型、选区追问、快捷操作、Codex 原生会话分叉和执行过程展示。原有上下文以完整文档或文档增量、选区和会话历史为基础，Codex 可以直接修改文件。以下六项能力在这个基础上扩展；系统保持单用户、单活动文档。

本设计保留 Markdown 文档作为主要成果载体，新增功能优先在现有文档区、节点内容区和讨论树中展开。功能描述以用户行为为主，不规定底层接口和存储实现。

讨论树记录问题、回答和推演路径。一条回答可能同时包含解释、风险、建议和多个执行步骤，用户可以选择其中一部分形成成果。因此，本设计弱化现有节点类型，不再为回答附加任务、决策、假设等分类状态机；交互围绕具体内容的采纳、引用和执行展开。

## 2. 主要概念

| 概念 | 用户可见含义 | 规则 |
| --- | --- | --- |
| 讨论节点 | 一次问题、回答及相关信息 | 可以继续追问、展开分支、被其他节点引用 |
| 父子关系 | 从某个节点继续推演的路径 | 延续现有分支和会话继承规则 |
| 引用关系 | 作为本次讨论依据的资料 | 不改变原节点的父子关系，也不自动合并会话 |
| 综合讨论 | 结合多个节点，在同一文档下新建的一段独立讨论 | 以综合要求为根问题，有自己的会话和讨论树；回答保留来源引用 |
| 修改提案 | 尚未写入文档的拟议修改 | 审核通过后应用，并记录来源及目标版本 |
| 执行记录 | 用户根据回答发起的一次执行及其结果 | 保存来源片段、执行要求、过程和结果，不把来源回答改为任务 |
| 操作记录 | 内容被引用、应用到文档或用于执行的记录 | 由真实操作产生，可以回看范围和目标，不由用户手工贴完成标签 |
| 项目 | 用户在玄鸟打开的本地目录 | 项目总览仅汇总该目录内的文档和事项 |

综合结论仍是一轮可继续追问的问答。一个节点可以被多处引用、产生多个修改提案或执行记录，各条记录关联具体片段并分别显示结果，原问题和回答保持原始身份。

同一原文选区可以关联原始讨论和综合讨论。“继续追问”沿用现有分支规则；“开启独立讨论”明确创建新讨论，不因原文选区相同而复用旧会话。引用或显示在附近，不表示继承另一段讨论的历史。

## 3. 功能一：可见、可选择的讨论上下文

### 3.1 功能目标

发送问题前，用户能看见本轮主动附加的资料，并明确它与已有会话历史的区别。支持引用其他章节、文档选段和讨论内容，减少重复复制粘贴。

### 3.2 界面与入口

在所有提问输入框上方增加“本轮参考”区域。默认折叠为一行摘要：

```text
本轮参考  [当前文档] [原文选区] [分支历史] [引用 2 项]  + 添加
```

点击展开后显示来源卡片：标题、来源类型、章节或节点路径、引用范围、版本状态，以及“查看来源”动作。用户添加的引用允许移除；系统自动提供的来源说明用途。

“完整文档背景”“分支历史”“原文选区”均可点击展开，在参考栏下方查看说明；“分支历史”按根问题到当前节点列出已保存问答，可逐项展开，不混入兄弟分支，并说明原生会话还可能包含执行过程；“原文选区”提供完整文本的滚动查看，位置失效时明确标记。查看操作不添加引用或改动草稿。再次点击、点击“收起”或按 Escape 可关闭，Escape 优先关闭内部展开项。

问题和回答的引用卡片使用“问题摘要 · 问题／回答”作为短标题，下面单独显示引用正文预览，展开后查看完整正文。标题不再拼接创建讨论时的原文长选区；来源路径和引用范围继续保留在详情中。标题只帮助识别来源，不代替实际引用内容。

第一阶段沿用普通追问提供当前完整文档或增量的方式，明确标出“完整文档背景”和“本次关注选区”。需要重新限定范围时，用户通过“开启独立讨论”选择“附带当前文档”或“仅附带所选资料”；原文锚点可以保留用于定位，但不会因此自动加入锚点正文。章节级自动裁剪后续再做。

### 3.3 使用流程

1. 用户选中文档段落并提问，系统自动展示当前文档、选区和分支历史。
2. 用户点击“添加”，搜索当前文档章节或讨论节点。P2 开放其他本地 Markdown 文档及其选段，入口位置保持一致。
3. 用户可以选择“整条回答”或“选中片段”，查看预览后加入引用。
4. 用户输入问题并发送，消息下方保存这轮实际附加的来源清单。
5. 查看历史消息时，点击引用可定位原位置，同时查看当时使用的内容快照。

已有内容还支持两种快捷方式：选中文字后点击“引用到输入框”；将选中文字拖入输入框，生成引用卡片。键盘和按钮操作应覆盖拖拽的全部功能。

### 3.4 上下文与历史规则

- 本次问题和用户明确要求决定任务范围。文档背景、引用及历史用于解释和支持问题，不因出现更多资料而自动扩大任务；界面按“本次要求 / 主动参考 / 既有历史”分层说明，不要求用户给资料逐项设置权重。
- 沿用分支时，明确展示“沿用本分支对话”。移除引用不承诺从模型历史中删除已发送内容。原生会话恢复失败、只能用本地问答重建时，额外显示“已根据本地问答重建，部分执行过程可能缺失”；历史来源能恢复多少就明确展示多少，不把重建过程称为完整恢复。
- 会话重建后如要继续修改文件，先按当前文件和必要的实际检查确认执行基础，不凭旧回答推断步骤已完成。资料缺失影响判断时明确说明，并让用户补充；普通阅读和问答不增加重复确认。
- 用户选择“仅附带所选资料”时，新讨论使用列出的资料和本次指令，不继承原分支对话，也不主动附带完整文档；模型自身配置和运行权限仍按现有设置生效。新讨论与来源通过引用关联。
- 文档范围限制描述主动提供的资料，不等同于限制 Codex 的文件读取权限。输入框的参考清单也不冒充 Agent 实际读取文件的完整清单，后者仍在执行过程中展示。
- 发送前引用固定到本轮版本。发送过程中源内容变化，不替换正在使用的快照。
- 来源 ID、版本、身份和字符范围由程序保存，用于查看来源、变化检查和安全回写。发给模型的引用只包含来源名称、路径及正文；同一次请求内，相同来源、相同范围和相同正文只提供一份，当前问题和重建历史通过简短参考编号对应。不同来源、不同范围或正文已经变化的快照分别保留，不因文字相同就合并；后续新请求仍可完整提供所选资料。
- 采纳提案中的来源回答与参考资料共用同一份正文。程序在文档中标出精确编辑范围或插入位置，模型只返回替换内容，无需计算字符偏移；正式回写仍由程序依据已保存的范围和版本校验。普通讨论用可读行号说明有效选区位置，同一行内存在相同文字时补充带临时选区标记的原文，避免修改错误位置；内部锚点不直接发给模型。
- 同一来源、同一范围重复添加时合并；移除卡片不删除原文或原节点。
- 每轮最多 24 项不同资料、合计 160,000 字符，包含作为操作依据的来源回答。重复来源先合并再计数，重试沿用完整清单不会把来源回答再算一次。
- 未发送的引用卡片允许查看差异并更新为新版；已经发送的消息固定使用当时快照，新版用于后续新消息，具体见第 8.4 节。来源已删除时，保留可用快照并显示“原位置不可用”。
- 同组、相邻、连线关联的其他节点只可作为“可补充资料”线索，不默认加入本轮参考。用户添加或 Agent 因当前问题按需读取后，再展示实际参考记录；固定参考视图也不改变此规则。
- 超出上下文预算时，发送前提示需要缩小哪些资料；不静默丢弃引用。长资料摘要必须经用户确认，并标记为摘要。

### 3.5 验收要求

用户能在发送前辨认文档范围、显式引用和历史继承方式；刷新后仍能查看历史消息当时的引用；移除引用、来源失效和独立讨论均有清晰反馈。会话降级重建可被辨认；“仅附带所选资料”不会额外注入完整文档或未选邻居。

## 4. 功能二：多分支比较与综合结论

### 4.1 功能目标

用户展开多个方案后，可以直接比较和收敛，形成有来源的结论，避免把大量回答手工汇总到另一段聊天中。

### 4.2 界面与入口

讨论树工具栏增加“选择节点”。进入后通过复选框多选；支持快捷键辅助多选和 Esc 退出。选择至少两个节点后显示：

```text
已选 3 个节点   [并排查看] [比较方案] [生成综合结论] [取消]
```

“并排查看”只调整界面，不调用 AI。“比较方案”和“生成综合结论”先打开准备面板，列出来源和可编辑要求，用户点击“开始”才执行。

两个生成入口使用同一个准备面板，区别仅在于预填的要求是比较差异还是给出建议，用户可以修改。并排查看始终保留完整选择列表，两栏各自选择当前展示项，例如“共选 3 项，当前查看 A、B”。切换查看项不增删参考资料，从该视图打开准备面板时带入完整选择列表。

### 4.3 使用流程

1. 用户选择“方案 A”“方案 B”和“性能风险”。默认引用每个节点的问题与回答，不自动包含其全部后代。
2. 准备面板分为“本次综合要求”和“参考资料”。除所选节点外，默认加入原讨论的根问题，标明“原始目标”，可查看或移除；根问题已经选中时去重。这样局部方案比较不会默认丢掉最初的问题。
3. 面板展示共同祖先路径，并提供“补充此前要求”的入口，用户可引用任一祖先中的具体片段，也可追加必要后代。未选的祖先不会自动送入模型。用户核对目标与约束、填写比较维度后，点击“开始”。系统展示最终资料清单，创建独立的综合讨论。
4. AI 输出比较结果、推荐及理由、关键分歧、证据缺口和后续验证项。
5. 系统打开同一文档下的新讨论，根问题保存用户提交的综合要求，回答展示结果和来源卡片。顶部提供“返回来源讨论”，源讨论的“相关讨论”入口也可以再次打开它。
6. 用户可继续追问、选取结论采纳到文档、引用到其他讨论，或根据其中的具体要求发起执行。

### 4.4 关系与会话规则

综合讨论有自己的会话和单根讨论树，以最终确认的资料清单构建上下文；默认不另行附带整篇文档，需要时从准备面板添加。源分支历史不会被隐式合并。综合讨论中的后续追问按现有父子、分叉规则继续，原树结构保持不变。

新讨论沿用来源讨论的原文锚点，作为定位线索；“采纳到文档”时仍须展示并确认实际修改范围。锚点失效时保留讨论并显示“原文位置已变化”，允许重新关联。不会任意选取某个方案节点作为综合讨论的父节点。

Tree 实线继续只表达父子推演关系。跨讨论引用通过来源卡片和返回链接访问，首期不增加跨树连线或多根画布；用户能查来源即可。

第一阶段只支持同一文档、同一讨论树内的多选收敛。跨讨论、跨文档来源后续通过“添加引用”选择，不要求用户同时展开多个树。

### 4.5 边界与异常

- 仍在生成回答的节点不能作为完整回答提交，选择列表注明“生成中”。
- 空回答、失败节点可引用已有文字，但应显示资料不完整。
- 多个资料互相矛盾时，结果保留分歧，不自动把其中之一标为事实。
- 当前要求与旧讨论约束不一致时，标明差异；用户明确修改过的要求以当前指令为准。不能确定旧限制是否仍有效时先澄清。原始问题较长时沿用上下文预算规则，不静默截断。
- 源节点更新后，综合结论标记“依据已更新”；用户可选择重新评估。重新评估生成新版本，不覆盖历史回答或已经应用到文档的内容。
- AI 推荐以回答呈现；只有实际应用修改后，才显示相应片段的文档应用记录。

### 4.6 验收要求

用户能完成多选、核对原始目标与祖先约束、预览范围、比较、回看来源和继续讨论；三个所选方案在双栏切换后均保留，另外附带的原始目标和约束单独列明。新综合讨论能独立打开、刷新和追问，不改变原分支历史；更新来源后不会静默重写结论。

## 5. 功能三：回答转成果与文档修改审核

### 5.1 功能目标

用户选择回答中的结论，生成文档修改提案，审核后应用，并记录从讨论到文档修改的对应关系。本节负责文档回写；引用和执行流程见第 6 节。

### 5.2 界面与入口

节点回答工具栏增加“采纳到文档”。选中回答片段时，也在选区浮层展示该入口。点击后选择以下写入方式：

| 动作 | 默认行为 |
| --- | --- |
| 替换原文 | 以当前讨论的文档锚点为目标，生成替换提案 |
| 插入到章节 | 选择章节和插入位置，生成插入提案 |

需要记录决策时，用户可以将结论、理由和取舍插入文档的决策章节，沿用同一提案审核流程。无需先把回答标记为“决策”。

### 5.3 修改提案使用流程

1. 用户选择整条回答或片段，点击“采纳到文档”，选择“替换原文”。
2. 系统显示目标文档、章节和原文范围；普通讨论和综合讨论均确认该范围，锚点无效时要求重新选择位置。开始生成前保存当前编辑，并以已保存的版本作为提案基础。
3. 用户可以补充要求，例如保留术语、压缩到三段、保持原章节结构。
4. 生成期间仅产出提案，不修改目标文件。
5. 进入审核视图，显示修改前后 Diff、来源节点和简要修改说明。
6. 用户选择“应用修改”“继续调整”或“放弃提案”。继续调整会更新提案并再次展示 Diff。
7. 应用成功后，系统更新文档和相关锚点，节点显示“1 处内容已应用到第 3.2 节”。点击可回看具体来源片段和该次 Diff；部分内容被应用不表示整条回答已被采纳。

初期按完整提案应用；多个互不依赖的段落可以拆成独立提案。部分应用能力在能保证段落依赖关系和锚点一致性后再开放。

准备草稿同时保存写入范围所依据的正文版本。关闭后重新打开、或准备期间正文发生变化时，保留整理要求和资料，明确提示重新选择目标；用户确认当前正文中的位置后才允许生成。“文档末尾”等位置也必须重新确认，不能把旧字符位置直接套到新正文。

### 5.4 修改状态与撤回

```text
生成中 → 待审核 → 已应用
              ↘ 已放弃
待审核 → 目标已变化 → 重新生成 / 重新定位
已应用 → 撤回检查 → 已撤回 / 需人工合并
```

审核期间目标文档发生变化时，旧提案不能直接覆盖新内容。界面展示“目标已变化”，允许查看差异、重新定位并生成新版提案。

撤回前比较当前文档与该提案应用后的版本。能够确定不会覆盖后续编辑时执行撤回；有冲突时进入逆向修改审核，保留后续工作。撤回不删除原讨论、审核记录或历史来源。

已保存的提案应在刷新后恢复，不因关闭面板而丢失；放弃提案也不删除来源回答。关闭面板不等于停止生成。首期同一文档的 Agent 回合串行进行，已有回合运行时可以准备提案草稿，生成、应用或撤回操作须等其收尾；收尾后重新校验目标版本，发生变化则再次审核。

“继续调整”提交后立即显示生成进度，并保持停止入口可用。停止完成后保留已保存的提案和过程，用户可补充要求再次调整。正文保存后若讨论元数据协调失败，恢复操作不得覆盖其间产生的外部编辑；保留当前文件并提示冲突。

### 5.5 与现有直接执行的关系

“采纳到文档”入口采用先生成提案、再审核应用的流程。“据此执行”和现有用户直接要求 Codex 修改文件的执行路径，仍可能直接写盘；界面必须显示“直接执行”，并展示回合结果。未经写入隔离的执行不能标成“待审核且尚未应用”。

第一阶段的提案审核和撤回限于活动 Markdown 文档，不承诺为整个仓库的任意命令提供事务回滚。权限审批继续沿用现有机制；批准工具运行不等于采纳文档结论。

### 5.6 验收要求

生成提案不改变文件；审核时能看到目标、来源和完整 Diff；重复点击应用不会重复插入；文档版本冲突会阻止覆盖；应用和撤回后锚点仍能正确定位。锚点失效不删除来源讨论及成果记录；生成过程中关闭面板、执行收尾后版本改变均能正确恢复或提示。

## 6. 功能四：从回答中采纳、引用或执行，并追踪结果

### 6.1 功能目标

让每个动作产生明确结果：继续讨论产生新问答，采纳产生文档修改，引用成为其他讨论的依据，执行产生过程和结果记录。用户无需先对回答分类。

### 6.2 操作设计

| 操作 | 使用方式 | 实际结果 |
| --- | --- | --- |
| 继续追问 | 选择回答片段或整条回答，输入问题 | 按现有分支规则新增问答 |
| 采纳到文档 | 选择结论及目标段落，审核提案 | 修改文档，保留应用位置、Diff 和来源 |
| 引用到其他讨论 | 选择片段及目标讨论，加入输入框 | 发送后建立可回看的来源引用 |
| 据此执行 | 选择具体要求，补充目标和验收条件，点击开始 | 发起一次执行，保存要求、过程、文件变化和结果 |

整条回答工具栏和选区浮层提供一致动作。有选区时默认使用选区，面板明确展示范围；无选区时预览整条回答。回答生成期间不提交尚未稳定的内容，可以继续阅读，生成结束后再操作。

### 6.3 据此执行的使用流程

1. 用户从“建议采用分块上传，需要验证断点恢复并补充重试机制”的回答中选中“验证断点恢复”，点击“据此执行”。
2. 准备面板展示来源片段和当前执行目录。用户填写或调整执行目标、必要限制及验收条件；可查看本轮参考资料和历史继承方式。
3. 点击“开始执行”后，先保存指令、来源快照及执行记录，再调用 Codex；保存失败时不启动。打开面板或保存输入草稿不会运行，也不会创建待办任务。已有回合执行时，面板保留草稿并显示“当前执行结束后可开始”，不隐式排队执行。
4. 系统按现有追问及分叉规则创建后续问答，保存本次明确指令，并附加执行记录。来源回答及原有后代不被改写；继承历史时沿用第 3 节的提示规则。
5. 执行区复用现有计划、工具、权限、文件变化和输出展示。可能直接修改文件时，清楚显示“直接执行”和当前权限设置。
6. 执行结束后展示结果、验收条件对应的验证证据以及尚未验证的部分。用户可以继续追问、补充验证或再次执行，不要求把来源节点标记为“任务完成”。

执行区提供“停止”。停止请求发出后显示“正在停止”，直到运行和文件变化协调完成，才显示“已中断”并允许再次执行。正常结束、失败或主动停止时保存已收集的过程和结果，不撤销已发生的文件修改。重试创建新的执行记录，并先检查当前文件状态；重复点击开始不能重复提交同一次执行。

### 6.4 引用与结果回看

“引用到其他讨论”打开目标选择器，可以选择已有讨论或新建独立讨论。选定后把来源卡片加入目标输入框，不自动发送。只有消息成功提交后，来源节点才显示“被引用”，避免把未发送草稿统计为成果。

节点卡片的主要内容仍是问题和回答，只在发生相关操作后显示简短记录：

```text
本轮：已回答
1 处内容已应用到文档 · 被 2 段讨论引用 · 关联 1 次执行
```

点击记录打开对应列表，再定位到来源片段、目标文档、引用消息或执行详情。每条记录保存内容版本和时间；回答后续修改不改变历史操作的依据。一次应用被撤回后记录显示“已撤回”，不再计入当前有效应用数量。

每篇文档提供轻量的“成果记录”入口，汇总该文档的提案、应用和执行，保证来源讨论删除后仍能找到记录。它与节点上的结果链接读取同一批记录，无需用户额外维护。

运行状态只表达正在生成、等待权限、正在停止、已结束、失败或已中断等实际进度；不能确认时按第 6.6 节显示未知结果。结果中记录哪些检查已通过、未通过或未执行；不能把运行结束表述为需求已完成，也不能把部分片段的应用表述为整条回答已采纳。

### 6.5 现有类型与快捷操作的调整

现有节点类型数据保留，作为可选历史标签弱化展示，不作为创建节点的必填项，也不决定工具权限、执行流程或项目待处理统计。原“转任务”快捷提示可以继续用于生成执行步骤，但仅生成回答；“据此执行”是另一个需要明确提交指令的动作。

本期不新增独立任务管理或决策台账。未来确有长期管理需求时，可以从回答中提取有独立身份、目标及生命周期的事项，并回链原回答，另行设计；不把这套管理模型施加到每条问答上。

### 6.6 刷新、停止与重启后的反馈

| 场景 | 用户看到什么 | 继续方式 |
| --- | --- | --- |
| 页面刷新，服务仍在运行 | 重连同一次执行，恢复服务保留的进度 | 继续观察或停止；不会再次提交指令 |
| 主动停止或已捕获的运行失败 | 已保存的过程、结果与中断或失败原因 | 检查当前文件后决定是否再次执行 |
| 服务退出，未能确认执行已结束 | 原始指令、来源和已落盘记录；显示“执行状态无法确认，结果需核对” | 查看当前文件和运行情况，确认原执行不会继续写入后，再决定是否执行 |

首期不承诺服务崩溃前每段工具输出都已保存；缺失部分明确显示“过程记录不完整”，不推断步骤未执行，也不自动重跑。若无法确认原执行是否仍存活，则阻止可能重复写入的重试并提示需要核对。运行已结束与验收条件是否得到验证继续分别展示。

以上规则覆盖普通问答、“据此执行”和 AI 新建文档。新建文档从准备快照开始即属于可停止操作；此时停止成功后，不再启动 Agent 或创建文件。原生连接意外丢失时保留原始请求及可核对的运行记录，不能只显示失败却没有恢复入口。

新建文档弹窗在创建期间提供“停止创建”和“后台继续”。关闭弹窗后创建继续进行，可从运行记录查看状态；停止不撤销已经创建的文件。重新准备时恢复原指令、目录和文件名要求，展示已知的创建路径与原结果，用户核对后再明确开始。创建请求绑定发起时的源文档，切换文档不会触发旧请求再次执行。

未知结果确认后仍保留历史标记，后续文档、消息与执行结果照常刷新。即使活动 Markdown 已移动或删除，也能核对运行、填写验证结论和删除已结束的记录。停止日志临时保存失败时保留恢复状态，存储恢复后可重试保存并完成核对，不要求等待失联回合自行返回。

再次执行按原始入口准备：普通问答保留原问题及上下文，新建文档保留建文档要求，从回答发起的执行保留来源回答。准备阶段允许查看和修改；显式开始后创建新的执行记录，旧记录与快照保留。

### 6.7 删除和改写后的成果保留

- 删除消息、子树或整段讨论时，已保存的应用、提案和执行记录保留在文档“成果记录”中；来源链接显示“原讨论已删除”，仍可回看该记录的来源快照。
- 删除引用的目标消息后，该引用不再计入来源节点的有效引用数量。已经保存的操作记录仍保留当时资料，不因目标删除而重写历史。
- 删除或大幅改写原文导致锚点失效时，保留讨论并提示重新定位，不自动级联删除问答和成果。这是对现有锚点删除行为的调整。
- 删除讨论不会撤回文档修改或中止关联运行。运行尚未收尾时禁用删除，先停止并完成收尾；确认删除时说明将保留哪些成果快照，避免用户误以为已彻底清除所有副本。
- 用户在“成果记录”中可以显式删除本地记录，删除前说明将失去该记录的回看及撤回入口；此动作不修改 Markdown，也不删除其他讨论中已经保存的引用快照。运行中记录不可删除。
- 删除成果内容后仍保留最小的请求去重信息，不包含指令、引用和输出正文。旧页面或网络重试再次提交同一请求时提示记录已删除；用户重新准备并开始的新请求才会执行。

### 6.8 验收要求

用户无需选择类型即可完成追问、采纳、引用和执行；每次操作能找到确切来源范围及结果；未发送引用不计入记录；一次回答可产生多项独立成果。刷新不会重复启动，正常失败和停止可回看过程，重启后未知结果不会被误判为安全重试；删除来源后仍能找到成果快照并独立清除记录。

## 7. 功能五：围绕当前动作调整工作视图

### 7.1 功能目标

让阅读、追问、比较、审核和全局浏览各自获得足够空间，同时保持用户的位置和输入连续性。

### 7.2 视图设计

在讨论详情顶部提供视图切换，保留现有三栏作为默认布局。

| 视图 | 主要布局 | 常用动作 |
| --- | --- | --- |
| 默认 | 文档、节点内容、讨论树 | 沿用当前三栏交互 |
| 专注讨论 | 放大回答和输入区，树收为当前路径 | 继续追问、添加引用、查看父节点 |
| 比较 | 完整选择列表加两个查看栏，展示来源路径 | 切换查看项、独立滚动、交换左右、引用选段、生成综合结论 |
| 审核 | Diff 为主，来源结论在可折叠侧栏 | 应用、调整、放弃、查看原文 |
| 总览 | 放大讨论树，详情按需打开 | 筛选、搜索、多选和定位 |

### 7.3 固定参考节点

节点详情提供“固定为参考”。固定后，用户点击其他树节点只切换工作面板，参考节点保持不变。两侧各自保存滚动位置，并提供“交换”“取消固定”和“引用到输入框”。

第一阶段同时保留一个参考节点。固定行为只影响显示，不自动把它加入 AI 上下文；需要发送给 AI 时点击“引用”。

从固定参考进入综合准备面板时，将当前节点与参考节点作为待确认资料列出，不直接发送。多选比较则始终使用完整选择列表；当前两栏显示什么不改变列表。

### 7.4 交互规则

- 切换视图保留输入草稿、当前节点、参考节点、文档位置和树的缩放位置。
- 页面内切换文档时，未发送的问题、引用和发送错误按文档分别保留；返回后恢复对应草稿，不混入其他文档。刷新页面后的未发送草稿恢复不属于本期承诺。
- 沿用当前单击树节点切换内容的习惯，点击“回到总览”恢复之前树的位置。
- 首次打开时工作节点位于画布可见区域；分栏和窗口尺寸变化时保持原来阅读的画布中心，不把节点推到屏幕外。
- 从比较视图开始生成综合结论时，先展示资料确认面板，不因并排展示而隐式提交资料。
- 打开审核提案时进入审核视图；关闭后返回此前的视图和节点。
- 宽度不足时用“工作内容 / 参考内容”页签切换，不强行挤压成窄三栏。
- 项目、成果与运行状态占用独立布局区域；进入讨论后使用讨论内的入口，不以悬浮工具条覆盖正文、引用按钮或输入区。
- 窄窗口中的长路径换行，长输出在局部区域滚动；关闭和提交按钮保持可达。嵌入审核面板的引用组件使用一致的深色主题。按 Escape 优先关闭当前引用选择或展开内容，再退出父面板。
- Esc 先关闭当前浮层，再退出多选或特殊视图，最后沿用现有退出详情行为。
- 按钮支持键盘操作，焦点位置清楚；不可只依赖颜色、悬停或拖拽完成动作。

### 7.5 验收要求

在讨论、比较和审核间切换不丢草稿、不重置阅读位置；固定参考不改变实际上下文；多于两项的比较不会丢失未展示资料；小窗口下仍能完成相同任务。

## 8. 功能六：项目讨论与成果总览、跨文档引用

### 8.1 功能目标

用户可以从项目层面找到最近讨论、待审核修改、实际执行和已应用成果，并追踪 PRD、RFC、ADR 等文档之间的依据关系。汇总依据为真实操作记录，不从回答类型推断未解决问题或未完成任务。

### 8.2 界面与入口

目录区增加“项目总览”，提供“最近讨论 / 修改提案 / 执行记录 / 已应用成果”切换。顶部汇总需要具体操作的记录，例如待审核提案、等待权限的执行及引用依据变化。

```text
项目总览
待审核修改 3   当前执行：等待权限   依据已更新 4

记录      标题             结果或状态   来源文档
修改提案  补充分块重试说明  待审核       upload.md
文档应用  采用分块上传      已应用       adr-07.md
执行记录  验证断点恢复      已结束       upload.md
```

列表支持按文档、记录种类、实际运行或提案状态及依据更新情况筛选。数量按对应记录去重计算；同一回答的两次执行计为两条执行记录，不计为两个任务。第一阶段汇总已建立讨论数据的 Markdown 文档，不扫描全文自动推断待办事项。

### 8.3 使用流程

1. 用户打开项目总览，选择“修改提案”并筛选“待审核”。
2. 点击某条提案先只读预览 Diff，保留来源节点入口；点击“打开文档处理”再切换目标文档。点击执行记录可直接只读查看过程和结果。
3. 用户完成审核或查看结果后返回总览，恢复原筛选条件和滚动位置。

从最近讨论打开文档处理时，恢复该讨论上次有效的工作节点；没有保存位置或节点已删除时定位到已有根节点。仅空讨论显示创建根问题，普通导航不自动聚焦输入框。
4. 在讨论中通过“添加引用”选择其他文档的章节或节点。
5. 被引用来源发生变化后，相关节点显示“依据已更新”。
6. 用户查看引用版本与当前版本的差异，选择“保留当前依据”或“用新版发起讨论”。后者打开预填新版资料的输入框，发送后才产生新的问答。

第一阶段保持单活动文档、单个执行中的 Agent 回合。项目总览和其他文档的只读预览不切换执行对象，也不关闭当前运行时。

“打开文档处理”、目录树切换和跨文档引用跳转遵守同一规则：存在运行、等待权限或正在停止的回合时，允许预览，暂不切换活动文档。界面提供“继续查看”和“停止当前执行”；停止完成后用户再次点击打开，系统保存当前编辑并切换。不会因为普通导航自动中断或自动重新发起运行。草稿保存失败时保留当前文档和输入，提示处理后再切换。

查看或引用其他文档无须启动其 Agent；需要在那里执行时先切换活动文档。首期不提供跨文档后台并行执行。

### 8.4 来源版本与变更提醒

引用同时保留来源身份、引用范围、当时内容和版本。已应用到文档的结论可以回看当时依据；当前来源变化也能被发现。

“依据已更新”表示来源内容发生变化，不自动断言结论过时。第一阶段只提醒直接引用该来源的节点，不自动沿关系传播提示或改写状态。

历史消息、应用和执行记录始终绑定实际使用的快照。“保留当前依据”只表示已查看并暂不处理此次版本差异，不声称结论已重新验证；该版本差异仍可回看，下次来源再次变化时重新提醒。“用新版发起讨论”默认创建独立讨论，带入新版资料和待评估的旧结论，用户可以补充要求；不原地替换历史引用。只有未发送草稿中的卡片使用“更新为新版”。

仅移动文档位置或重映射选区、引用正文未变化时，不应误报内容更新。发现文件重命名但无法确定身份时提示重新关联；不静默把引用指向同名文件。

从历史引用点击“查看原位置”时，跨文档来源先以只读方式展示文件和准确的问答或正文片段；点击“打开文档处理”才切换活动文档。重新关联已改变目标的路径需要显式选择当前文件，历史引用继续保留原身份；新消息须重新选择当前来源，不能仅凭内容相同接续旧引用。

来源增长到超过单轮资料预算时，版本检查仍返回变化状态、检查时间和新版版本，不影响同批其他引用。界面保留历史快照并提示从新版选择更小片段，不自动截断来源，也不提供无法发送的整篇新版引用。

源文件删除后保留历史快照，显示“来源不可用”；删除项目索引中的记录不应删除原 Markdown。项目外引用单独标注，并不计入项目内部事项统计。

外部修改被检测到后及时更新提示；若尚无文件监听能力，则在打开文档、进入总览和手动刷新时检查，并显示最近检查时间。界面不能在未实现监听时宣称实时同步。

### 8.5 验收要求

数量与提案、执行、引用和应用记录一致，不统计“决策节点数”或“任务节点完成率”；点击记录能够定位来源和结果；返回总览保留筛选。执行期间预览其他文档不中断运行，真正切换遵守统一规则；来源更新、删除、移动后不丢失历史依据，采用新版只影响新消息。

## 9. 六项功能串联的使用示例

场景：用户正在完善一份上传服务 RFC。

1. 选中“上传失败后整体重试”，引用需求文档中的大文件场景，提问是否需要分块上传。输入框展示本轮资料和历史范围。
2. 从根问题展开“整体重试”和“分块重试”两个分支，分别讨论复杂度及失败成本。
3. 固定第一个方案作为参考，并排阅读第二个方案，将关键测试结果加入引用。
4. 多选两个方案和讨论风险的回答，在准备面板核对原始目标，并引用祖先问答中的“兼容现有客户端”要求。新建综合讨论，回答列出推荐、取舍和未验证条件，并保留来源。
5. 用户选中“采用分块重试”的结论及理由，点击“采纳到文档”，确认实际目标段落，审核 RFC 的 Diff 后应用。
6. 从回答中选中“验证断点恢复”，点击“据此执行”，填写目标和验收条件并开始。执行结束后查看测试证据；缺少验证时继续追问或补充执行。
7. 执行期间用户可从项目总览只读查看需求文档，执行继续进行。需求引用内容变化后，点击“用新版发起讨论”准备重新评估；原结论和应用记录保留旧依据。

这一流程中，Tree 始终记录问答及分支；引用、文档应用和执行各有明确动作、来源范围和结果，不要求用户给回答贴任务或决策标签。

## 10. 实施优先级与交付边界

| 阶段 | 交付内容 | 阶段完成标准 |
| --- | --- | --- |
| P0-A：上下文透明 | 来源清单、同文档引用、历史引用快照、独立讨论入口、会话重建提示 | 用户知道实际附加的资料及历史范围，独立讨论不会误复用旧会话 |
| P0-B：成果回写 | 活动 Markdown 的提案生成、Diff 审核、版本校验、文档成果记录、安全撤回及运行中切换保护 | 一条回答能被审阅、应用并追溯；锚点或来源删除不丢成果 |
| P1-A：分支收敛 | 同树多选、原始目标和祖先引用、双栏比较、新建综合讨论 | 多条分支能形成独立可追问的结论，实际引用的资料和约束可核对 |
| P1-B：回答操作与结果追踪 | 据此执行、停止与收尾、刷新重连、重启后核对、运行及验证结果展示 | 用户能发起一次明确执行，识别中断和未知结果，避免重复写入 |
| P1-C：视图优化 | 固定参考、专注讨论、统一视图切换和位置恢复 | 完成比较和审核时无需反复切换、复制内容 |
| P2：项目关联 | 跨文档引用、讨论与成果总览、依据变化提醒 | 可从项目查看提案、执行和文档应用，定位到来源及结果 |

文档“成果记录”、删除保留规则及运行期间的切换保护随 P0-B 交付，覆盖已有目录导航，不等待项目总览。提案审核的基础视图随 P0-B 交付，双栏比较随 P1-A 交付，其余视图切换在 P1-C 完善。主动停止随 P1-B 交付；此前需要等待当前回合收尾才能切换。P2 在此基础上增加跨文档只读预览、引用和项目汇总。

本期不承诺多人协作、自动跨 Agent 调度、任意仓库操作回滚或所有文档的自动知识抽取。这些能力需要独立产品设计与范围评审。

## 11. 评审与体验验证

用第 9 节的完整场景验收，并重点观察：

- 用户能否在发送前准确说出本轮参考范围和历史继承方式。
- 比较多个方案时，是否仍需大量复制粘贴和来回切换。
- 从讨论结论到应用文档修改，是否能连续完成且找回来源。
- 用户能否直接从回答片段采纳、引用或执行，并分清回答已生成、修改已应用、执行已结束及验证是否通过。
- 来源变化时，用户能否找到受影响结论，并选择是否重新评估。

补充以下边界场景，作为相应阶段的产品验收用例：

| 场景 | 预期结果 |
| --- | --- |
| 原问题要求不新增依赖，仅选择两条局部方案综合 | 准备面板可见原始目标和祖先路径，实际带入的约束可核对 |
| 选择三项资料，在双栏中轮流查看后综合 | 最终资料清单仍包含三项，不因展示切换而遗漏 |
| 综合讨论刷新、继续追问、采纳原文 | 保持独立讨论身份，能返回来源，采纳前明确目标段落 |
| 原生会话无法恢复 | 展示问答重建提示，继续执行前核对必要文件状态 |
| 执行等待权限时打开另一篇文档 | 可只读预览；活动文档不切换，权限和运行不被销毁 |
| 文件可能已修改，服务却在回合结束前退出 | 保留已落盘资料，标明结果需核对，不自动重跑 |
| 删除已有应用记录的来源讨论或原文选区 | 应用记录仍可在文档中回看，文件不回滚；选区失效可重新关联 |
| 已应用结论的依据从 v1 更新到 v2 | 旧记录保留 v1，用 v2 评估生成新消息，不伪造历史依据 |

本设计不要求新增遥测。可通过本地演示、人工体验记录和后续实现验收验证上述目标。
